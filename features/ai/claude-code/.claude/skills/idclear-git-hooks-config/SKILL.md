# idclear git-hooks configuration

Two layers run on every commit and push in this repo. This skill covers how to **configure** them — not the workflows that consume them.

## The two layers

| Layer | Source of truth | Generated artifact | Runtime |
|-------|-----------------|--------------------|---------|
| `prek` hook entries | `.cursor/nix/features/git-hooks-prek.nix` → `git-hooks.nix` (cachix submodule) → `hook.nix` typed submodule | `.pre-commit-config.yaml` (symlink to nix-store JSON, regenerated on `devenv up`) | `pkgs.prek` |
| Devenv hook scripts (`pre-commit`, `pre-push`, `commitizen`) | `.cursor/nix/features/git-hooks-moon.nix` (`preCommitTargets` / `prePushTargets` strings) | `scripts.pre-commit.exec` / `scripts.pre-push.exec` in devenv shell | `moon` on devenv shell PATH |

The `prek` config invokes the devenv scripts by name (`entry = "pre-commit"`), so a change to either layer can affect what runs at hook time.

## prek hook options that matter

`git-hooks.nix` (cachix) exposes a typed submodule per hook at `modules/hook.nix`. Options relevant to idclear:

| Option | Effect |
|--------|--------|
| `enable` | include the hook entry |
| `entry` | command to run |
| `stages` | which stages fire (`pre-commit`, `commit-msg`, `pre-push`, `manual`, …) |
| `pass_filenames` | whether to append changed file paths |
| `always_run` | run even when no files match `files`/`types` regex |
| `language` | `system` invokes `entry` directly; other languages go through toolchains |
| `verbose` | **print hook stdout/stderr even on success** (default: capture and only show on failure) |

`prek` is the Rust reimplementation of `pre-commit` and honors every option the Python version does. The full schema serializes through to the generated JSON verbatim (see `modules/hook.nix` line 259 — the `raw` attrset inherits `id name entry language files types types_or exclude_types pass_filenames fail_fast require_serial stages verbose always_run args`).

## Recipes

### Make hook output visible (verbose mode)

Default prek captures each hook's stdout/stderr and only prints on failure — same UX as Python's pre-commit. To surface passing-hook output (useful for `:lint` / `:test` runs that are mostly silent on green), flip `verbose = true` on each hook entry:

```nix
# .cursor/nix/features/git-hooks-prek.nix
hooks = {
  commitizen.enable = true;

  pre-commit = {
    enable = true;
    name = "pre-commit";
    entry = "pre-commit";
    stages = ["pre-commit"];
    pass_filenames = false;
    always_run = true;
    language = "system";
    verbose = true;          # <-- add this
  };

  pre-push = {
    enable = true;
    name = "pre-push";
    entry = "pre-push";
    stages = ["pre-push"];
    pass_filenames = false;
    always_run = true;
    language = "system";
    verbose = true;          # <-- and this
  };
};
```

After `devenv up` (or any `devenv shell`), the symlinked `.pre-commit-config.yaml` regenerates from this with `"verbose": true` on each entry.

For commitizen specifically, leave `verbose: false` — its only output is the commitizen success banner, which is noise.

If you want verbose behavior transiently without editing nix, run prek directly with `-v/--verbose`:

```bash
prek run --verbose -t pre-commit
```

This is the right tool when debugging a single hook invocation.

### Add a new hook

1. Add the entry under `hooks.<name>` in `.cursor/nix/features/git-hooks-prek.nix`. Required fields: `enable = true`, `name`, `entry`, `language`.
3. If the entry is a devenv script (e.g. `pre-commit`, `pre-push`), the script itself is generated by `git-hooks-moon.nix` — coordinate the two files.
4. Verify the JSON regenerated correctly: `cat $(realpath .pre-commit-config.yaml)` should show your hook with `"verbose": <your choice>`.

### Swap which moon targets the pre-commit/pre-push scripts run

The hook **scripts** live in `.cursor/nix/features/git-hooks-moon.nix`. Override the targets at the consumer side (`devenv.nix`):

```nix
cursor.features.git-hooks-moon = {
  enable = true;
  preCommitTargets = ":lint :test --affected remote --cache off";
  prePushTargets = ":lint :test :coverage --affected remote --cache off";
};
```

The `--affected remote --cache off` pattern matches `.definitively/programs/pre-commit.yml` — keep the two files aligned so `definitively run pre-commit` and `git commit` exercise the same targets.

## Pitfalls

### `verbose` change doesn't take effect until next `devenv up`

`.pre-commit-config.yaml` is a symlink to a nix-store JSON. The JSON is only regenerated when devenv re-evaluates the shell (which is what `devenv up` / `devenv shell` do). After flipping `verbose = true`, force a shell regen:

```bash
devenv shell -- bash -c 'cat $(realpath .pre-commit-config.yaml) | grep -A1 pre-commit'
```

If the JSON still shows `"verbose": false`, the nix eval didn't run, or your edit was outside the consumer module's import chain (see `.cursor/nix/README.md` "Enable API").

### `git commit` invokes prek via the cache, not the live config

`prek install` snapshots the config at install time into `.git/hooks/`. If you change `.pre-commit-config.yaml` and don't re-run `install-git-hooks` (or `prek install -f`), the live hook still uses the old config. The devenv `enterShell` calls `install-git-hooks` on every shell entry — that's why CI-style one-shot invocations should run through `devenv shell --` rather than a bare terminal.

### `git push` from a non-devenv shell fails on `.cursor` submodule

The `.cursor` submodule's own pre-push script (set up by `.cursor/nix/features/git-hooks-moon.nix` inside the submodule) calls `moon run :lint :test :coverage --affected remote --cache off`. From a plain Nix shell where moon isn't on PATH, push dies. Workarounds in order of preference:

1. `devenv shell -- bash -c 'cd .cursor && git push origin main'`
2. `git push --no-verify` for config/doc tweaks (document this in the reply so the user can re-run the gate manually).
3. Patch the submodule's pre-push to tolerate missing moon — out of scope unless asked.

See `submodule-sync` for the full submodule push flow.

### `DEVENV_PROFILE` set ≠ devenv shell activated (most common prek failure outside CI)

`git-hooks-prek.nix` defines hook entries with `entry = "pre-commit"` / `"pre-push"` and `language = "system"`. These resolve to devenv-generated scripts in `$DEVENV_PROFILE/bin/`. **They only work when that directory is on `PATH`.**

`DEVENV_PROFILE` being exported in your shell is **not** sufficient evidence that those scripts are reachable. A common failure mode (this session): devenv was activated in a parent shell, the user started a new Hermes session that inherited `DEVENV_PROFILE` and `DEVENV_ROOT`, but the new shell's PATH only contained the standalone `~/.nix-profile/bin`. Result:

```
$ git commit -m "..."
prek hook-impl ... --hook-type=pre-commit ...
Using config file: .../.pre-commit-config.yaml
error: Failed to run hook `pre-commit`
  caused by: Run command `run system command` failed
  caused by: No such file or directory (os error 2)
```

Diagnosis, in order:

```bash
# 1. Does devenv think the shell is active?
echo "DEVENV_ROOT=$DEVENV_ROOT DEVENV_PROFILE=$DEVENV_PROFILE"

# 2. Is the profile bin on PATH?
echo "$PATH" | tr ':' '\n' | grep -F "$DEVENV_PROFILE/bin"

# 3. Are the devenv scripts reachable?
command -v pre-commit; command -v pre-push
```

If step 2 is empty, the shell is in a "set-but-not-sourced" state. Fix: re-enter via `devenv shell` (or `devenv up`) so the eval profile prepends `$DEVENV_PROFILE/bin`. A bare `export PATH="$DEVENV_PROFILE/bin:$PATH"` works as a one-shot but doesn't trigger the rest of the shell wiring — prefer `devenv shell`.

Don't diagnose this from the error message alone — it looks identical to a missing binary, a broken hook symlink, or a malformed `entry`. Check PATH first, then the symlink in `.git/hooks/`.

### `monorepo:format` fails with "These paths were provided but ignored" — even though the files match biome's include list

Symptom (from `monorepo :format` or `treefmt --config-file treefmt.ci.toml`):

```
Formatted 0 files in 1338µs. No fixes applied.
format ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  × No files were processed in the specified paths.
  i Check your biome.json or biome.jsonc to ensure the paths are not ignored by the configuration.
  i These paths were provided but ignored:
  - .hermes/shell-hooks-allowlist.json
```

Exit code 1 → moon `:format` fails → `pre-commit` script (which runs `moon run :lint :test :coverage --affected remote --cache off`) aborts. **The misleading part**: every file was *ignored*, but biome still treats "all inputs ignored" as a failure (not informational).

Root cause is a two-layer include/ignore mismatch:

1. `treefmt.{toml,ci.toml}` `[formatter.typescript]` (the `biome` formatter) has `includes = ["*.json", ...]` — broad by design.
2. `biome.json` `files.includes` has `"!.hermes", "!.cursor", ...` — biome correctly excludes `.hermes/`, `.cursor/`, etc.
3. treefmt doesn't know about biome's ignore list. It walks the repo, finds `.hermes/shell-hooks-allowlist.json`, and hands it to biome. biome sees the file on its CLI, ignores it per config, and exits 1 with the "provided but ignored" notice.

The fix is at the treefmt layer (not the biome layer) — filter the file out before biome sees it. Both `treefmt.toml` and `treefmt.ci.toml` need it; they use slightly different glob styles:

```toml
# treefmt.toml — exclude in the live config (single-star)
[formatter.typescript]
excludes = [
  "**/node_modules/**/*",
  "**/dist/**/*",
  "**/*.mjs.map",
  "**/biome.json",
  ".vscode/**",
  ".cursor/**",
  ".hermes/**",                 # <-- add
]

# treefmt.ci.toml — CI variant uses double-star inside
excludes = [
  "**/node_modules/**/*",
  "**/dist/**/*",
  "**/*.mjs.map",
  "**/biome.json",
  "**/.vscode/**/*",
  "**/.cursor/**/*",
  "**/.hermes/**/*",            # <-- add
]
```

Mirror biome.json's ignore list (`.cursor`, `.hermes`, `**/.next`, etc.) whenever you add a new repo-wide exclusion there — otherwise every "ignored by biome.json" file becomes a silent format-gate failure.

Note: the same class of bug applies to ANY treefmt formatter whose `includes` is broader than the underlying tool's own config. If you add a new formatter that delegates to another linter/formatter, mirror the tool's own `ignore` list into treefmt's `excludes` for that block.

Diagnostic shortcut when you hit this class of error:

```bash
# Confirm biome exits 1 on fully-ignored input
biome format --write --config-path=biome.json <path-the-treefmt-passed-in>

# Confirm treefmt passes the file at all
treefmt --config-file treefmt.ci.toml --allow-missing-formatter 2>&1 \
  | grep -F <path-the-treefmt-passed-in>     # should NOT appear after the fix
```

### Lean-ctx escapes project root for hook-related work

`modules/hook.nix` lives at `/nix/store/<hash>-source/modules/hook.nix`. To inspect it, add `/nix/store/<hash>-source` to lean-ctx `~/.config/lean-ctx/config.toml` `extra_roots` / `allow_paths`, then re-index. Don't `cat` it through the terminal — the routing-hook skill prefers MCP reads over shell text-tools.
